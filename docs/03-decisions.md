# Decisions

**Who this is for:** reviewers, and anyone asking "why does it work this way?"

To change a decision, don't edit its row. Add a new row that replaces it, and mark the old one "Replaced by N".

| # | Problem | What we picked | What we get | Why not other ways | Cost | Status |
|---|---|---|---|---|---|---|
| 1 | A waiting message must go back to the queue it came from, but delay queues are shared. | The message carries its queue's name. RabbitMQ reads it and sends the message back by itself. | No extra code or step: RabbitMQ moves it back by itself. All queues share the same delay queues. | Our own code moving it: more code, one more place to lose a message. Delay queues per queue: far too many queues. | One extra exchange, one binding per queue. | Accepted 2026-11-10 |
| 2 | With classic queues, a message whose wait is over can be lost silently if the move fails. | Quorum queues. They keep the message until the move has worked, with copies on more than one server. | A message isn't lost when a move fails. It waits until the problem is fixed. Losing one server loses nothing. | Classic queues: simpler and cheaper, but can lose messages. Local testing only. | More memory and CPU. A message can arrive twice. Tested on RabbitMQ 4.x only. | Accepted 2026-11-10 |
| 3 | The library must say "done" only after the retry copy is stored (decision 6). | One method. It runs the app's code, then says "done", plans a retry or parks the message. | One small method to learn. The app can see exactly what happens on an error. Easy to test. | Annotation or wrapper: harder to test, hides a setting the app must turn on. Spring's error handler: runs too late. | The app must turn on manual ack mode. The library can't check it. | Accepted 2026-11-10 |
| 4 | RabbitMQ can't "send this message later". | One delay queue per wait time (1 minute, 2 minutes, 4 minutes, ...). Nothing gets stuck behind a longer wait. | Short waits never wait behind long ones. Only a few queues, however many tries. Plain RabbitMQ, no plugin. | One queue with a wait per message: short waits get stuck behind long ones. A plugin: extra install, not as safe. RabbitMQ 4.3's own retry: waits grow slowly, stops by tries only, keeps no history. The README says when it's the better choice. | A few extra queues (4 in the example). A message can come back a little late, never early. | Accepted 2026-11-10 |
| 5 | Outages are measured in time, not tries. Some errors never go away. | Check in order: an error that can never succeed (park now), the time limit from the first failure, then a safety limit on tries. The parked message says which one stopped it. | Teams set the limit in time, the way they think about outages. A bad message is parked at once, with the right reason. Queues with different limits can share delay queues. | Count tries only: you can't tell how long that is. Each app handles its own: every team writes the same code. | A paused app can run a retry a bit after the time limit. | Accepted 2026-11-10 (the "never succeeds" part 2026-11-09) |
| 6 | If we remove the original before the copy is stored, a crash loses it. | Store the copy, wait for RabbitMQ to say "stored", then remove the original. No "stored" means the original is parked. | A message is never lost while RabbitMQ is healthy. If something breaks, the message is parked, not lost and not stuck in a loop. | Remove first: a crash in between loses it. Put it straight back: it fails again and again, very fast. | A message can arrive twice. The app's code must be safe to run twice. | Accepted 2026-11-10 |
| 7 | Waiting retries must survive restarts, show their history, and not slow the app down. | RabbitMQ holds waiting and parked messages. Each message carries its history. Any copy of the app can pick it up. | Retries survive restarts and deploys. The app keeps working on new messages during an outage. Copies of the app can be added or restarted at any time. Parked messages can be checked and sent again. | Resilience4j or Spring Retry: fine for quick retries, but a restart loses longer ones. Kafka: can't delay one message at a time. Redis: a crash can lose the message. A database and timer: one more system. | The app's code must be safe to run twice (R-4). Resilience4j still fits inside the app's code for quick retries. | Accepted 2026-11-10 |
| 8 | A message that stops retrying needs somewhere to wait until a person looks at it. | Each queue gets its own parking queue (`orders` parks in `orders.dlq`). | Each team sees only its own broken messages. After a fix, everything in `orders.dlq` goes straight back to `orders`, with no sorting. An alert on `payments.dlq` says exactly which queue is in trouble. Each team can be given access to its own parking queue only. | One shared parking queue: works, because each message carries its queue's name, but every team digs through everyone's messages, and replay needs sorting first. | One extra queue per app queue. Cheap, since parking queues are usually empty. | Accepted 2026-11-10 |
| 9 | R-5 needs queues with different time limits, for example 30 minutes for one and 2 hours for another. | The top-level settings are the defaults. Each queue under `queues` can override any of them. | Shared values are written once. A queue changes only what's different. | One set of settings for all queues: R-5 can't be met. A list of queue objects: more typing for the common case. | A queue name with dots needs brackets in YAML. | Accepted 2026-11-10 |

## Details for developers

1. Header `x-original-queue`, headers exchange `<p>.return`, bindings with `x-match=all-with-x` (plain `all` skips headers that start with `x-`). The Phase 2 test checks the header survives the move.
2. Delay queues set `x-dead-letter-strategy=at-least-once`, `x-overflow=reject-publish` (without it RabbitMQ falls back to the unsafe way) and an `x-max-length`. A full delay queue refuses the retry, and the original goes to the parking queue.
3. `void handle(Message message, Channel channel, MessageWork work) throws IOException;` with `@RabbitListener(ackMode = "MANUAL")`. Retries go out on the library's own connection.
4. Queue-level `x-message-ttl`. The settings decide how many queues. Settings that need too many stop startup.
5. `retry-ladder.non-retryable`, `window`, `max-attempts`, header `x-first-failed-at`. Reasons: `non-retryable`, `window`, `attempts`. See 02-design.md section 2.
6. Publish with `mandatory=true` and a publisher confirm, wait up to `confirm-timeout`. Ack only if confirmed and not returned, otherwise reject with `requeue=false`.
8. One direct exchange `<p>.dlx`. Each `<queue>.dlq` is a durable quorum queue, bound with routing key `<queue>.dlq`. The app's queue sets `x-dead-letter-exchange=<p>.dlx` and `x-dead-letter-routing-key=<queue>.dlq`.
